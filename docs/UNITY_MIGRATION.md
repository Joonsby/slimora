### 재미없게 느껴지는 원인 (코드에서 나온 것)

1. **본편 전투는 1 : 1 이다.** 슬라임 한 마리와 몬스터 한 마리가 번갈아 친다. 대상 선택 · 위치 · 역할이 끼어들 자리가 없다.
2. **용병은 「슬라임 공격력 × 비율」을 더하는 공격 타이머다.** 8종의 차이는 `power` · `intervalMs` · 패시브 수치뿐이고, 치명 · 흡혈 · 화상도 없다. 탱커 · 회복 · 광역이 존재하지 않으므로 **편성은 선택이 아니라 가장 높은 숫자 고르기**다.
3. **진화 3종이 각각 효과 하나다.** 흡혈 · 피해감소 · 화상 중 지금 스테이지에 맞는 것을 고르는 정도라 플레이 방식이 바뀌지 않는다.
4. **200스테이지는 같은 공식의 곱셈이다.** 3계열 몬스터가 이름 · 색만 바뀌어 반복된다. 스테이지 수가 콘텐츠 양을 뜻하지 않는다.
5. **전략적 판단은 던전에만 있다.** 스킬 선택 · 시너지 · 필살기 타이밍은 던전이 가장 잘 만들어져 있지만, 본편 경제와 분리된 부가 콘텐츠다.

## 2. 유지 · 개선 · 재설계 · 제거 · 후순위

| 분류 | 대상 | 이유 |
|---|---|---|
| **유지** | 결정적 엔진 구조(예정 시각 순 · 시드 난수) · JSON 데이터 · 저장 봉투(스키마 버전 · 체크섬) · 보상 장부(주문 ID · 던전 runId) · 오프라인 = 실제 엔진 표본 | 장점이 분명하고 이미 테스트가 있다 |
| **개선** | 도전 던전(스킬 · 시너지 · 보스 패턴) · 필살기 예고-끊기 · 오프라인 보상 시각 검증 | 잘 만들어졌지만 본편과 이어지지 않는다 |
| **재설계** | 본편 전투(1:1 → 분대 대 무리) · 용병(공격 타이머 → 역할) · 진화(효과 1개 → 플레이 방식) · 스테이지 구조(200 곱셈 → 적 조합이 다른 구간) | 1장의 원인 1~4 |
| **제거 후보** | 용병 패시브 중 골드 배율(조합보다 경제에만 작용) · 스테이지 이름만 다른 구간 | 선택을 만들지 않는다. 확정은 Phase 1 검증 후 |
| **후순위** | 환생 · 뽑기 · 랭킹 · 결제 · 광고 | 핵심 전투가 재미있다는 것이 확인된 뒤에 얹는다 |

## 3. Unity 구조

```
unity/
  Slimora/                         Unity 6 프로젝트 (패키지는 uGUI + 내장 모듈만)
    Assets/Slimora/Core/           규칙 계층 — asmdef noEngineReferences: UnityEngine 참조 불가
      Rng.cs · MiniJson.cs          mulberry32 · FNV-1a · JS 수치 함수(Math.round · ToInt32 · String(n))
      Legacy/                       본편 전투 엔진 이전본 (engine.ts · damage.ts · stats.ts 몬스터 쪽)
      Squad/                        리뉴얼 프로토타입 전투 (역할 기반 분대)
      Diagnostics/Parity.cs         TS 벡터 대조 — dotnet · 에디터 · WebGL 공통
    Assets/Slimora/Runtime/        표현 계층 — 엔진 이벤트를 연출로만 바꾼다
      SlimeBody.cs                  정점 스프링 소프트바디 메시
      UnitView.cs · BattleDirector.cs · Hud.cs · DamagePopup.cs · SafeAreaFitter.cs
    Assets/Slimora/Editor/SlimoraBuilder.cs   씬 · 프리팹 · 임시 아트 · 플레이어 설정 생성, WebGL 빌드
    Assets/Slimora/Resources/       squad.json(프로토 데이터) · Vectors/(TS 엔진 출력)
    Assets/WebGLTemplates/Slimora/  세로 전체화면 · 줌 금지 템플릿
  CoreTests/                       dotnet 콘솔 — Core 소스를 그대로 컴파일해 회귀 · 시뮬레이션
  tools/export-vectors.ts          TS 엔진으로 벡터 생성 (client 코드를 import, 수정 없음)
  tools/serve-webgl.mjs            빌드 결과 로컬 서버
```

- **규칙은 MonoBehaviour 에 없다.** `Slimora.Core` 는 엔진 없이 컴파일된다 (`CoreTests` 가 그 증거)
- **데이터 구분:** 밸런스 수치는 JSON 유지(기존 파일 그대로 · 서버 · 도구와 공유). ScriptableObject 는 아트 참조(스프라이트 · 프리팹 · 이펙트 · 사운드) 묶음에만 쓴다 — 수치를 SO 에 넣으면 TS 쪽 도구와 회귀 벡터를 잃는다
- **설정 공유:** C# 은 장 데이터 조립 규칙을 다시 짜지 않고, TS 가 편 결과(`config.json`)를 읽는다. 조립 규칙이 바뀌면 벡터를 다시 뽑으면 된다

## 4. 결정성 — TS ↔ C# 를 같게 만든 것들

| 위험 | 처리 |
|---|---|
| `Math.round` (JS: .5 → +∞) vs C# 은행원 반올림 | `JsMath.Round` = `floor(x)` 후 차이 ≥ 0.5 면 올림 |
| `x \| 0` · `>>>` · `Math.imul` | `unchecked` uint 곱 · 시프트로 비트 단위 동일 (난수 453개 일치) |
| `**` (V8) vs `Math.Pow` | 현재 데이터 범위(1.2^199 등)에서 결과 반올림 후 일치 확인 — **플랫폼별 libm 차이는 이론상 남는다.** WebGL 에서 따로 대조한다 |
| 숫자 → 문자열 (회귀 비교용) | **런타임마다 다르다.** .NET 8 `"R"` = 최단, Mono `"R"` = 17자리, Mono `"G16"` 는 반올림이 틀린다. `BigInteger` 로 ECMAScript 최단 왕복 표기를 직접 구현 (node 표기 18,016개와 일치) |
| 계산 순서 | 이벤트 · 행동 선택 순서(화상 → 슬라임 → 몬스터 → 보스 시간 → 용병)를 그대로 옮기고 이벤트 열 전체를 해시로 비교 |

## 5. 앱인토스 · WebGL

- 공식 Unity SDK: `im.toss.apps-in-toss-unity-sdk` (`https://github.com/toss/apps-in-toss-unity-sdk.git`), 최소 2021.3 · 권장 Unity 6+. Build & Package 로 `.ait` 생성, 압축은 Brotli 권장
- 금지: iframe 삽입(반려). `createUnityInstance()` 로 직접 렌더링
- 알려진 이슈: 6000.1.8 미만 Rigidbody2D GC 누수 — 6000.6.8 은 해당 없음, 프로토타입은 물리를 쓰지 않는다
- SDK 의 `AIT.*` API 는 일반 브라우저에서 동작하지 않는다 — 샌드박스 앱 또는 `.ait` 업로드 후 토스 앱 QR 로만 확인 가능

## 6. 저장 · 보상 안전성 — 서버 없이 보장 못 하는 것

| 항목 | 클라이언트만으로 | 한계 · 서버 설계 |
|---|---|---|
| 스키마 버전 · 손상 | TS: 봉투 버전 + 체크섬 + v1~v8 이전. **Unity 프로토는 아직 미이전** (PlayerPrefs 에 범위 검사만) | — |
| 던전 · 주문 중복 지급 | TS: runId · orderId 장부. **Unity 미이전** | 저장 파일을 되돌리면 장부도 되돌아간다 → **IAP 는 서버 주문 장부 필수** |
| 오프라인 시간 조작 | 지금은 기기 시계 · 저장 시각 차이. 되감기는 거부, 앞으로 감기는 막지 못한다 | `Environment.getServerTime`(SDK) 로 기준 시각을 받으면 서버 없이 완화. 완전한 방어는 서버 시각 |
| 클라이언트 변조 | 막을 수 없다 (체크섬은 손상 감지용) | 랭킹 · 재화 판매가 커지면 서버 권위 필요 |
| 광고 보상 | SDK 보상 이벤트 후 지급 · 일일 횟수 | 서버 측 보상 콜백(SSV)이 SDK 에 있는지 **미확인** |
